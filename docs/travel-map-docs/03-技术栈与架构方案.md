# 03｜技术栈与架构方案

## 1. 已确认的方向

- 产品形态：**桌面应用** ✅ 已确认  
- 平台：**Windows + macOS** ✅ 已确认  
- 部署路径：**先完成本机闭环，上云保留为后续阶段** ✅ 已确认  
- 内容：站内编辑上传（文字 + 图片 + 文档）✅ 已确认  
- 地图交互：省份镜头缩放平移，城市点击不移动镜头 ✅ 已确认  
- 桌面外壳：**Electron** ✅ 已确认  
- 在线底图（第一阶段）：**高德地图（AMap）** ✅ 已确认  

## 2. 桌面外壳（已选）

### 2.1 Electron ✅ 已确认
适配“站内编辑上传 + 附件管理 + 双平台”的需求：
- 文件系统与窗口能力成熟（拖拽导入、选择文件夹、预览、打开外部文件）
- 自动更新、权限、媒体处理等生态完善
- 全 JS/TS，学习与迭代成本更低

## 3. 地图渲染与交互

### 3.1 推荐基线：SVG + D3（适合你的交互，且可离线）
- 省/市边界：SVG `<path>`，天然可点击、好做描边高亮
- 镜头缩放平移：d3-zoom 控制整体 `transform`
- POI 点：SVG circle / icon + tooltip

### 3.2 在线能力（第一阶段采用高德）
第一阶段采用 **高德地图（AMap）** 来获得国内更贴近实际的：
- 道路/卫星底图
- POI 搜索与详情
- 地理编码/逆地理编码（地址↔坐标）
- 路线规划（可选，后续按需接入）

接入后通常可获得：
- 在线底图瓦片、道路/地形/卫星等样式
- 地理编码/逆地理编码（地址↔坐标）
- POI 搜索与详情
- 路线规划（驾车/步行/公交）与距离/时间估计

注意（通用）：
- 需要申请 Key，且通常**依赖联网**；离线/长期缓存瓦片可能有平台限制（需看各家条款）
- 坐标体系多为 **GCJ-02/BD-09**，需要统一你的内部坐标存储策略（见《05-未决问题清单》）
  - ✅ 已确认：数据库内部统一存 **WGS84**
  - 因此需要在边界层做坐标转换：高德（GCJ-02）↔ 数据库（WGS84）

### 3.3 性能关键点（无论 SVG 或地图 API 叠加层）
- 底图数据简化（TopoJSON 或简化版 GeoJSON）
- 按需加载：全国省级常驻；进入省才加载该省地级市

## 4. 数据层（先本机闭环，后续预留上云扩展）

### 4.1 本机（第一阶段）
- 数据库：SQLite（单机、简单可靠）
- 附件：存本机应用数据目录（按 asset_id 管理）

### 4.2 上云（后续规划，暂不纳入当前实现）
- 数据库：若未来需要多端，再评估 Postgres（或继续 SQLite 单用户）
- 附件：若未来需要对象存储，再评估 Cloudflare R2
- 身份认证：仅在引入多设备访问时再设计

> 原则：前端不直接依赖“文件路径细节”，通过统一的 Asset 服务访问，便于迁移。

## 5. 生产/开发构建（概念）

- UI：前端（React/Vue 等）+ 地图组件
- 桌面：Electron Main（系统能力）+ Renderer（前端界面）
- 数据：本机 SQLite + 本地文件存储（附件）
