# 11｜R2 同步与上传队列（后续规划，暂不实现）

> 说明：当前版本只聚焦本地上传、本地阅读与本地备份闭环。本文件仅保留为未来若恢复上云需求时的设计草案，不作为当前实现范围。

## 1. 当前状态

- 暂不实现 R2 上传、同步队列、`remote_url` 写回与多设备访问。
- 若未来恢复该方向：
  - 所有密钥仅通过环境变量或主进程安全配置提供，不进入前端 bundle
  - 上传/删除动作仅允许由主进程执行

> 备注：如果未来要发布给他人或做 Web 端，再优先评估“Worker 签名 Presigned URL”的薄后端模式。

## 2. 未来若恢复上云时的队列设计

### 2.1 触发时机（异步）
当本地文件写入成功且 SQLite 写入 Asset 成功后，将 `asset_id` 推入上传队列（Queue）。

### 2.2 并发控制
- 并发度建议：3~5（避免拥塞）

### 2.3 重试策略
- 默认不做复杂断点续传（单图通常 <10MB）
- 上传失败：标记为 pending 并重新入队（或下次启动继续）
- 建议记录：失败次数、最后失败时间、最后错误信息（便于 UI 提示）

### 2.4 写回策略
上传成功后：
- `UPDATE Asset SET remote_url = ? WHERE asset_id = ?`

## 3. 未来若恢复上云时的对象命名与删除

### 3.1 对象 Key（建议）
建议把对象 key 设计成“稳定且不需要重命名”的形式：
- 使用 `{assetId}__{original_filename}` 或 hash/uuid 前缀
- 避免未来改名导致远端迁移

### 3.2 删除一致性
当应用内触发 Asset 物理删除时（见《09》）：
1) 先删本地文件
2) 若存在远端对象：调用 SDK `deleteObject`
3) 最后删除 Asset 数据库记录

> 远端删除失败：记录日志并允许后续重试（不阻塞本地删除）。

## 4. 当前替代方案

当前阶段通过以下能力完成闭环：
- 本地附件落盘
- `local://` 资源加载
- 应用内本地阅读/打开
- zip 全量备份与恢复

也就是说，当前版本不依赖任何云端对象存储就可以完成日常使用与迁移。
