# 2026-05-10 城市工作台运行时闭环修复设计

## 背景

当前城市工作台已经具备 `visit_state`、城市级未归类资料、旅行记录与本地预览的基础结构，但用户在真实 Electron 运行时仍遇到以下问题：

- 点击 `想去` / `去过` 提示更新状态失败
- 点击 `快速导入资料` 后没有明确反馈，底部仍显示“城市资料加载失败”
- 点击 `开始记录` 后，在旅行列表里点 `新建` 没有反应

这些问题说明当前实现还存在运行时闭环缺口，主要集中在数据入口边界、文件选择链路和错误反馈三个方面。

## 问题归因

### 1. 数据入口边界不清晰

当前 `db:getCity` 在“读取城市详情”的同时，还负责隐式写入 `Province` 和 `City`。这会导致以下副作用：

- `updateCityVisitState`
- `createTrip`
- `saveCityAsset`

这些写操作事实上依赖“之前已经成功调用过一次 `db:getCity`”，否则就可能因为缺少 `City` / `Province` 记录或状态不同步而失败。

这是典型的隐式前置条件问题，不利于维护，也会让错误表现变得随机。

### 2. 文件导入链路过度依赖 `File.path`

当前城市工作台和旅行详情页多个上传入口都直接创建浏览器 `input[type=file]`，再从 `File.path` 中读取本地路径。该方式在 Electron 环境中并不稳定，且当路径缺失时当前实现通常直接跳过：

- 不抛错
- 不提示失败原因
- 不统计跳过数量

最终用户感知为“选了文件但没有反应”。

### 3. 错误反馈不完整

当前多个关键入口在失败时只做 `console.error`，没有明确反馈：

- `TripList` 新建旅行失败
- 部分上传动作路径为空
- 运行时能力异常时的前端行为

这会把“真实失败”伪装成“按钮没反应”。

### 4. 状态文案混淆

当前 `CityHome` 和 `CityAssets` 会把多类失败都折叠成泛化文案，例如“城市资料加载失败”或“本地资料加载失败”，无法区分：

- 运行时 IPC 能力异常
- 数据库写入失败
- 真实空数据
- 文件导入失败

这会误导排障方向。

## 目标

本轮修复只解决本地闭环运行时问题，不引入上云、同步或远程存储能力。

目标如下：

1. `visit_state` 切换在真实 Electron 环境中可稳定写入
2. `快速导入资料` 提供明确反馈，并能在 `本地资料` 中立刻看到结果
3. `开始记录 -> 新建` 可以稳定创建旅行并进入详情页
4. 城市页和资料页明确区分“空状态”和“失败状态”
5. 去除“先读一次城市才能写”的隐式前置条件

## 非目标

- 不改动城市工作台的信息架构
- 不扩展新的云端同步模型
- 不新增完整独立文件管理器
- 不调整 Trip / POI 的核心业务模型

## 方案概述

本轮修复拆成四个模块：

### 模块 A：显式城市存在性保证

新增主进程内部复用函数，例如：

- `ensureProvinceExists(...)`
- `ensureCityExists(...)`

其职责是：

- 保证 `Province` 存在
- 保证 `City` 存在
- 在不覆盖用户已写入摘要、封面等内容的前提下，同步基础名称信息

该保证函数应由以下入口直接调用，而不是再依赖 `db:getCity` 的副作用：

- `db:getCity`
- `db:updateCityVisitState`
- `db:createTrip`
- `file:saveCityAsset`

这样，无论用户先点状态、先点导入，还是先点新建旅行，都能独立成功。

### 模块 B：文件选择链路改为主进程驱动

将城市工作台上的快速导入与封面选择从“前端直接读 `File.path`”改为优先使用主进程文件选择器 IPC。

建议新增或复用以下能力：

- `file:select` 扩展为支持：
  - 单文件 / 多文件
  - 图片过滤
  - 通用文档过滤

渲染层只负责：

- 请求用户选文件
- 获得真实本地路径数组
- 调用 `saveCityAsset` 或 `saveAsset`
- 汇总导入成功数、失败数、失败原因

这样可以避免对浏览器文件对象实现细节的依赖。

### 模块 C：前端状态与错误反馈补齐

需要补齐以下反馈：

- `updateVisitState` 失败时显示具体错误消息
- `TripList.handleCreate` 失败时 toast 提示
- 快速导入时：
  - 选中文件但没有可导入路径
  - 部分成功、部分失败
  - 全部失败
  都要有明确反馈

同时，页面状态改为更清晰的几类：

- `loading`
- `runtime_error`
- `data_error`
- `empty`
- `ready`

若页面失败但基础工作台仍可显示，则错误块需要给出具体原因，而不是笼统写“城市资料加载失败”。

### 模块 D：结果刷新与页面联动

完成写操作后，前端需要显式刷新相关数据：

- 更新 `visit_state` 后刷新 `CityHome`
- 导入成功后刷新 `CityHome` 与 `CityAssets`
- 新建 Trip 成功后：
  - 进入 `TripDetail`
  - 旅行列表可立即读到新数据
- 资料归入旅行后刷新资料列表与当前选中项

本轮不引入全局事件总线重构，维持当前局部刷新模式，但要避免“写成功、界面不刷新”的假空态。

## 详细设计

### 1. 主进程：城市存在性保证

新增内部工具函数，放在主进程 DB 或 IPC 附近的可复用位置。

输入：

- `provinceId`
- `provinceName`
- `cityId`
- `cityName`

行为：

- `INSERT INTO Province ... ON CONFLICT DO UPDATE`
- `INSERT INTO City ... ON CONFLICT DO UPDATE`

约束：

- 只更新基础名称字段
- 不覆盖 `summary`
- 不覆盖 `cover_asset_id`
- 不重置 `visit_state`

调用原则：

- 所有依赖 `City.city_id` 外键或城市状态写入的入口，都要在写之前显式调用

### 2. 主进程：快速导入与旅行创建

#### 快速导入

`file:saveCityAsset` 在执行保存前先确保城市存在。

完成后返回结构统一为：

- `ok`
- `assetId`
- `error`
- `originalFilename`

渲染层按返回值汇总结果，避免只能判断 `assetId` 是否为空。

#### 创建旅行

`db:createTrip` 在写入前先确保城市存在，避免受 `db:getCity` 调用顺序影响。

推荐补充最小校验：

- `city_id` 必填
- 若缺失则抛出可读错误

### 3. 渲染层：运行时能力守卫

新增渲染层工具函数，例如：

- `hasTravelMapApi()`
- `assertTravelMapApi()`

用途：

- 在关键页面初始化时判断 `window.travelMap` 是否可用
- 在关键动作触发前做快速失败

展示策略：

- 若能力缺失，不显示“数据库失败”
- 显示明确文案，如“当前运行环境不支持本地数据操作，请使用 Electron 启动应用”

即使用户本轮实际使用的是 Electron，这层守卫仍然保留，防止未来再次混淆。

### 4. 渲染层：城市工作台反馈

#### 状态切换

- 点击状态按钮后进入短暂提交态
- 成功后立即更新 UI
- 失败时 toast 显示主错误，必要时附带 `err.message`

#### 快速导入

新的交互规则：

1. 点击按钮
2. 通过主进程选择一个或多个文件
3. 若取消选择，则静默结束
4. 若选中但没有任何有效路径，则 toast 提示“未获取到可导入文件路径”
5. 导入完成后：
   - 全部成功：成功 toast，并跳转 `本地资料`
   - 部分成功：成功 toast + 失败详情
   - 全部失败：错误 toast，不跳转

### 5. 渲染层：旅行列表反馈

`TripList.handleCreate` 调整为：

- 新建中禁用按钮
- 创建失败时 toast 显示错误
- 创建成功后立即调用 `onSelectTrip(newTripId)`

空态文案保持不变，但不能再出现点击后毫无反馈。

## 测试与验证

### 自动化验证

优先补充或更新以下测试：

- 主进程：
  - `ensureCityExists` 不覆盖用户内容
  - `createTrip` 可在无预先 `getCity` 的情况下成功
  - `updateCityVisitState` 可在缺少城市记录时补齐并成功写入
- 渲染层：
  - 运行时能力守卫
  - 导入结果汇总逻辑
  - `TripList` 创建失败反馈

### 手动验收

必须手点验证以下路径：

1. 进入一个从未打开过的城市，直接点 `想去`
2. 进入另一个新城市，直接点 `开始记录 -> 新建`
3. 进入第三个新城市，直接点 `快速导入资料`
4. 导入后进入 `本地资料`，确认能看到 `未归类资料`
5. 新建旅行后，将未归类资料归入旅行

## 风险与取舍

### 风险 1：接口参数不完整

如果 `updateCityVisitState`、`createTrip`、`saveCityAsset` 当前只拿到 `cityId`，则无法单独完成 `ensureCityExists`。

取舍：

- 需要补充这些入口所需的 `provinceId` / `provinceName` / `cityName`
- 这是必要的显式化成本，优先于继续依赖隐式副作用

### 风险 2：前后端返回结构不一致

当前部分接口返回裸值，部分返回对象。

取舍：

- 本轮只在必要接口上做最小统一
- 不做全量 API 重构，避免扩大范围

## 实施顺序

1. 抽出 `ensureCityExists` 并接入主进程写路径
2. 修文件选择 IPC 与快速导入链路
3. 修 `CityHome` / `TripList` / `CityAssets` 的状态和错误反馈
4. 补测试并做手动验收

## 预期结果

修复完成后，城市工作台的三个首要入口：

- `想去 / 去过`
- `快速导入资料`
- `开始记录`

都应在“首次进入一个全新城市”的情况下直接可用，不再依赖其他页面先完成隐式初始化，也不再以“看起来没反应”的方式失败。
